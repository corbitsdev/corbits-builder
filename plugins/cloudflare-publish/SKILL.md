# Publish an app to Cloudflare

This ready-made plan publishes the project's saved app to Cloudflare, where people open it at its own workers.dev address, in three steps: cloudflare ready, cloudflare publish, then the cloudflare live check.

Run cloudflare ready first. It passes when the app is made to run on Cloudflare Workers. When it fails, the app needs changing, not anything at Cloudflare: start coder change with what the check's evidence names, asking for the app to run on Cloudflare Workers as the Workers skill packs describe, then run cloudflare ready again. The person is never asked to do anything technical for it.

The person's go-ahead is their press of Publish, on the publish screen or in the conversation. When they press it on the screen, Builder adds this plan with their go-ahead. When they ask you in their own words, add this plan yourself and Builder asks them in the conversation. Either way publish agreed then passes and cloudflare publish starts without asking again. Run publish agreed if cloudflare publish is refused for it; nothing is published until it passes.

Once their go-ahead stands, start cloudflare publish. If there is neither a saved Cloudflare token nor an acceptance of Cloudflare's terms, Builder first shows the person the Publish to Cloudflare screen (cloudflare account), where they choose to publish without an account or with their own, and starts the publish once they answer. Each acceptance makes one temporary account, so the next publish without an account shows the screen again; the app then goes to a new address, and the earlier one can no longer be kept from Builder. Publishing changes to the same app needs their own account, after they kept the app from the screen that shows where the app is published.

The publisher reports the address people open the app at and, without an account, how long they have to keep it. If it says the app is published but its address is not answering yet, the publish is done: relay that it may take a little longer to start answering. When the app cannot be published, the run ends blocked with a reason written for the person: relay it. When the reason says the app does not fit Cloudflare, install or build, the next step is coder change, then this plan's ready and cloudflare publish again under the same go-ahead. When it names something they do in their Cloudflare dashboard or on the Publish to Cloudflare screen, start cloudflare publish again once they say they did it. Open the Publish to Cloudflare screen yourself only when the reason says to.

Once the publish reports the address, run cloudflare live. It passes while the published app is the one saved now, and the plan ends when it does. A newer saved version makes it lapse until that version is published too, which the person asks for anew.

To take the app down, the person confirms Take it down, on the publish screen or in the conversation once you add cloudflare remove to the plan for them; Builder then records their go-ahead, puts cloudflare remove on the plan with it and tells you. Run cloudflare removable, then start cloudflare remove, which takes no input. When cloudflare remove ends blocked, relay its reason; once they say they dealt with it, run cloudflare removable again and, while it passes, start cloudflare remove again without asking again. Their go-ahead stops counting once the app is published again, so a later take-down needs Take it down again. Builder cannot take down an app in a temporary account the person never kept: Cloudflare removes it by itself once the time to keep it runs out. Without a saved token, Builder first shows the person the Cloudflare account screen, which then asks only for a token for the account the app is in. If they never kept it, there is nothing to take down: tell them Mark as gone on the publish screen clears it.
