# Publish an app to the person's own server

This ready-made plan publishes the project's saved app to a server the person rents, in four steps: the server ready check, publish confirm, server publish, then the server live check.

Run server ready first. It passes when the app says how it runs in production: how it installs, builds and starts, and which folders keep what people enter. When it fails, the app needs changing, not the server: start the coder's change of the app to make it ready to publish, naming what the check's evidence says, then run server ready again. The person does nothing for it.

Then run publish agreed. If it passes, the person's go-ahead for this publish stands: go on without asking again. If it fails, open publish confirm with this plan's handle; nothing is published without their go-ahead there, and publish confirm says how long it lasts.

Once they go ahead, start server publish. If no server is connected yet, Builder first shows the person the connect screen, which gives them a key for their hosting provider and asks for the server's address, and starts the publish once they connect it. The publisher readies the server if needed, publishes the app and reports the address people open it at.

When the app cannot be published, the run ends blocked with a reason written for the person: relay it. Open the connect screen again when the reason says to; for a server already saved it shows the key to give the hosting provider again, and connecting another server makes a new key that replaces the saved one. When the reason names something they fix at their hosting provider, such as opening the server's firewall, or a problem with Builder itself, start server publish again once they say they did it or ask to try again. When it says the app did not install, build or start, the app needs fixing and nothing on the server does: the next step is the coder's own check or change of the app, so that it installs, builds and starts from a clean copy, then server publish again under the same go-ahead. The person is never asked to work inside their server or to fetch anything from it.

Once the publish reports the address, run server live. It passes while the release Builder recorded for the server is the app as saved now, and the plan ends when it does. A newer saved version makes it lapse until that version is published too, which the person asks for anew.

To take the app down when the person asks, open publish take-down with this plan's handle. It shows them what goes and what is kept, and asks them to agree; the screen records their answer, never you. If they agree, run server removable, then start server remove, which takes no input. If they keep it, nothing is taken down. When server remove ends blocked, relay its reason; once they say they dealt with it, run server removable again and, while it passes, start server remove again without asking again. Their answer stops counting once the app is published again, so a later take-down asks again.
